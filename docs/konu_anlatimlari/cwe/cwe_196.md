# 👾 CWE-196 — Unsigned to Signed Conversion Error

> **İşaretsizden işaretliye hatalı dönüşüm.** Bir sayı işaretsiz bir tipten
> işaretli bir tipe aktarılır. Bitler değişmez — ama artık onları okuyan başka
> biridir ve aynı desene başka bir sayı der.

| | |
|---|---|
| **Resmî ad** | Unsigned to Signed Conversion Error |
| **Üst sınıf** | [CWE-681](./cwe_681.md) — Incorrect Conversion between Numeric Types |
| **Nerede doğar** | [09 · Subtraction](../salterden_bilgisayara/09_subtraction.md) — ikinin tümleyeni |
| **Zincirdeki yeri** | **196** → [839](./cwe_839.md) → [195](./cwe_195.md) |

---

## Dönüşüm Bitleri Değiştirmez

09. dersin bütün fikri tek cümlede duruyordu: **desen aynı, anlam okuyanın
kararı.** Bu CWE, o cümlenin hataya dönüştüğü an.

16 bitlik şu deseni al:

```
1111 1111 1111 1111
```

- **İşaretsiz okursan:** `65535`
- **İşaretli okursan:** `−1`

İkisi de doğru. Desen bir şey iddia etmiyor; sayıyı okuyan karar veriyor.

Şimdi bir programın şunu yaptığını düşün:

```c
unsigned short a = 65535;
short          b = a;        // aynı 16 bit, yeni okuyucu
                             // b artık −1
```

> 🔑 Burada **hiçbir bit kaybolmadı.** Kopyalama tam ve kayıpsız. Değişen tek şey,
> o 16 bite hangi kuralla bakıldığı. Hata, verinin kendisinde değil — **verinin
> hangi sözleşmeyle okunacağına dair anlaşmazlıkta.**

---

## Neden Tehlikeli

Tek başına `−1` üretmek zararsızdır. MITRE'nin tanımı tehlikenin nerede
başladığını açıkça söylüyor: büyük işaretsiz değerlerin işaretliye çevrilip
**dizi indeksi** ya da **işaretçi aritmetiği** olarak kullanılması.

Sebebi şu: işaretsiz dünyada **eksi yoktur**, sıfır tabandır. İşaretli dünyada
vardır. Dönüşüm, "asla eksi olamaz" varsayımıyla yazılmış bir kontrolün altından
eksi bir sayı sokar.

```c
short i = indeks_al();     // dışarıdan gelen değer −1 oldu
buf[i] = x;                // buf[−1] → tamponun BAŞINDAN ÖNCESİNE yazma
```

> ⚠️ Dikkat: burada tamponun **sonundan sonrasına** değil, **başından öncesine**
> yazılıyor. [CWE-787](./cwe_787.md#i̇ki-yön-sonrasına-ve-öncesine)'nin iki
> yönünden az konuşulanı bu. MITRE de 196'nın tipik olarak *buffer underwrite*
> koşullarını öncelediğini yazıyor.

## Zincirin İlk Halkası

196 yalnız çalışmaz. 09. derste anlatılan örnekte üç adımın ilki:

```
     ağdan 65535 gelir
            │
     ┌──────▼──────┐
     │   CWE-196   │  işaretli değişkene konur  →  −1 olur
     └──────┬──────┘
     ┌──────▼──────┐
     │   CWE-839   │  kontrol sadece üst sınıra bakar  →  −1 geçer
     └──────┬──────┘
     ┌──────▼──────┐
     │   CWE-195   │  kullanımda yeniden işaretsiz okunur  →  65535 bayt
     └─────────────┘
```

Üç ayrı numara ama tek bir kök: **aynı sayı üç kez farklı sözleşmeyle okundu.**

---

## Dürüst Bir Not

MITRE'nin CWE-196 sayfasında **gözlenmiş örnek (CVE) listelenmiyor** — kardeşi
[195](./cwe_195.md)'in aksine. MITRE'nin kendi ifadesiyle bu yön, işaretliden
işaretsize dönüşüme göre *daha az yaygın*.

Bu, "tehlikesiz" demek değil; "kayıtlarda daha az görünüyor" demek. İkisi aynı şey
değil. Bir zayıflığın CVE tablosunun boş olmasının iki sebebi olabilir: ya gerçekten
nadir çıkıyordur, ya da çıktığında başka bir numarayla etiketleniyordur — burada
büyük ihtimalle sonucu doğuran taşma ya da sınır dışı yazma raporlanıyor.

## Nasıl Önlenir

Kalıp, bu ailenin geri kalanıyla aynı: **dönüşümü yaptırmadan sor.**

```c
if (a > SHRT_MAX) return HATA;   // çevirmeden ÖNCE sığıyor mu diye bak
short b = (short)a;
```

Yanına pratikte şunlar ekleniyor:

- **Genişliği belli tipler kullan:** `uint16_t`, `int32_t` gibi. `short`un kaç bit
  olduğu derleyiciye ve platforma göre değişir; belirsizlik hatanın yarısıdır.
- **Derleyiciye söylet:** `-Wconversion -Wsign-conversion` bu dönüşümleri uyarı
  olarak yüzüne çıkarır. Varsayılan olarak açık değildirler.
- **Sınırı bir kez seç, her yerde aynı tipi kullan.** Bu ailenin bütün vakaları
  "aynı değer iki farklı tiple dolaşıyor" cümlesiyle başlıyor.
