# 👾 CWE-367 — Time-of-check Time-of-use (TOCTOU) Race Condition

> **A race between the moment of checking and the moment of use.** The program
> checks a resource, likes the answer, and uses it. If the resource changes in the
> gap between the two, the answer in your hand belongs to the past.

## A Check Is Not an Answer, It Is a Photograph

The program does this:

```c
if (access(path, R_OK) == 0)   // ① check: "am I allowed to read this?"
    fp = fopen(path, "r");      // ② use:   I read it
```

The logic looks flawless. But the time that passes between ① and ② is not zero. In
that gap, what `path` points at can be changed.

> 🔑 What the check gives you is not a **permission** but a **photograph**: "at that
> instant, this was the state." You act on the photograph, but the action is applied
> not to the photograph but to **reality**. Reality may have changed in between.

The fact that these are two separate system calls is not an accident, it is **the
structure itself**: in one you ask, in the other you act. There has to be a gap
between them.

---

## The Same Mistake, Three Faces

In this folder, three separate CWEs now say "there was a check and it did not
help" — and all three for **different reasons**:

| CWE | What the check got wrong |
|---|---|
| [**190**](./cwe_190.md) (BEC Token) | Asked the right question of an **already-overflowed** number — the order was wrong |
| [**839**](./cwe_839.md) | Asked about **half** the range — watched the ceiling, ignored the floor |
| **367** | Asked the right question of the right value — but at the **wrong moment** |

> 💡 Recognising these three together turns the question "is there a check?" into
> "**what, when, and of which value** is the check asking?" In an audit, that is the
> question that actually earns its keep.

---

## Why It Is Hard to Close

MITRE writes the structural problem underneath plainly: **file operations are split
across separate system calls, and for many scenarios there is no atomic
"check-and-use" primitive.** In other words the gap does not come from
carelessness; it comes from the interface itself.

Out of this comes a very common but wrong reflex: *"let me narrow the gap, put
nothing in between, make it fast."*

> ⚠️ **Narrowing the gap is not a fix.** The attacker does not have to hit it the
> first time; because a retry costs almost nothing, they can try hundreds of times.
> The narrower the gap, the lower the chance per attempt and the higher the number of
> attempts — the outcome does not change.
>
> We built the same reasoning in [CWE-1247](./cwe_1247.md): on the Xbox 360 the
> attack working one boot in four was **enough**, because the device could be
> switched on again and again. "Sometimes works" and "works" are the same thing to an
> attacker.

## MITRE's Recorded Examples

| CVE | What happened |
|---|---|
| **CVE-2015-1743** | Sandbox bypass: the file is replaced **after verification and before execution** |
| **CVE-2008-2958** · **CVE-2008-1570** | TOCTOU makes it possible to bypass a symbolic-link defence |
| **CVE-2003-0813** | A multi-threaded race leads to the use of memory that has been freed |

> 💡 The first is the clearest description of this weakness: the verification was
> done **correctly**, the result **was correct**, and that is precisely why it was
> trusted. Then the file changed. The last row shows that TOCTOU is not only about
> files — when the same gap occurs in memory, what comes out is
> [use-after-free](./README.md#on-the-way--the-alu-unit-and-beyond).

---

## How It Is Prevented

MITRE's first recommendation is surprisingly direct:

> **Do not perform a pre-check.** Validation before use creates false confidence.

That is: instead of asking with `access()` and opening with `open()`, **open it
directly and look at the result.** The act of opening already enforces permissions,
and that enforcement is atomic.

```c
fd = open(path, O_RDONLY | O_NOFOLLOW);   // ask + act, in one step
if (fd < 0) return ERROR;
fstat(fd, &st);                           // validation now happens on the DESCRIPTOR
```

The difference is subtle but decisive: after the second line, what you hold is not a
**name** but an open **file descriptor**. A name can be changed; a descriptor stays
bound to the object it was bound to. The attacker has nothing left to change.

Added on top:

- **Prefer atomic calls.** `mkstemp`, `openat`, `O_EXCL | O_CREAT` — each collapses
  "check and act" into one step.
- **Take the lock BEFORE the check**, not after.
- **Drop privileges.** Even if you lose the race, a process that cannot write cannot
  do harm.
- **Verify afterwards.** Once the operation is done, confirm that you really touched
  the right object.

## Summary — Keep in Mind

```
☐ A check is not a permission, it is a photograph: "at that instant, this was the state".
☐ The action is applied to reality, not to the photograph; reality can change in between.
☐ The gap is not carelessness but a STRUCTURAL consequence of separate system calls.
☐ Narrowing the gap is not a fix — the attacker retries for free (see CWE-1247).
☐ Three separate "there was a check and it didn't help": 190 wrong order, 839 half the range, 367 wrong moment.
☐ CVE-2015-1743: the verification was correct, the result was correct, then the file changed.
☐ Not only about files; the same gap in memory produces use-after-free.
☐ MITRE's first recommendation: DO NOT PRE-CHECK, it creates false confidence.
☐ Instead of access() + open(), open directly: opening already enforces permissions atomically.
☐ A name can be changed, an open descriptor cannot. Validate on the descriptor.
☐ Where it meets CWE-59 has its own number: CWE-363.
```
