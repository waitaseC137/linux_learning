# 👾 CWE-196 — Unsigned to Signed Conversion Error

> **Incorrect conversion from unsigned to signed.** A number is moved from an
> unsigned type into a signed one. The bits do not change — but the thing reading
> them now is different, and it calls the same pattern a different number.

| | |
|---|---|
| **Official name** | Unsigned to Signed Conversion Error |
| **Parent class** | [CWE-681](./cwe_681.md) — Incorrect Conversion between Numeric Types |
| **Where it is born** | [09 · Subtraction](../salterden_bilgisayara/09_subtraction.md) — two's complement |
| **Its place in the chain** | **196** → [839](./cwe_839.md) → [195](./cwe_195.md) |

---

## A Conversion Does Not Change the Bits

The whole idea of lesson 09 sat in one sentence: **the pattern is the same, the
meaning is the reader's decision.** This CWE is the moment that sentence turns
into a bug.

Take this 16-bit pattern:

```
1111 1111 1111 1111
```

- **Read it unsigned:** `65535`
- **Read it signed:** `−1`

Both are correct. The pattern claims nothing; whoever reads the number decides.

Now suppose a program does this:

```c
unsigned short a = 65535;
short          b = a;        // the same 16 bits, a new reader
                             // b is now −1
```

> 🔑 **Not a single bit was lost here.** The copy is complete and faithful. The
> only thing that changed is the rule used to look at those 16 bits. The bug is not
> in the data — it is in a **disagreement about the contract the data is read
> under.**

---

## Why It Is Dangerous

Producing a `−1` on its own is harmless. MITRE's definition says plainly where the
danger starts: large unsigned values cast to signed and then used as an **array
index** or in **pointer arithmetic**.

The reason is this: in the unsigned world **there is no negative**, zero is the
floor. In the signed world there is. The conversion slips a negative number under
a check that was written on the assumption "this can never be negative".

```c
short i = get_index();     // a value from outside became −1
buf[i] = x;                // buf[−1] → a write BEFORE THE START of the buffer
```

> ⚠️ Note: this writes not **past the end** of the buffer but **before its start**.
> It is the less-discussed of
> [CWE-787](./cwe_787.md#two-directions-past-the-end-and-before-the-start)'s two
> directions. MITRE also writes that 196 typically precedes *buffer underwrite*
> conditions.

---

## The First Link of the Chain

196 does not work alone. In the example from lesson 09 it is the first of three
steps:

```
     65535 arrives from the network
            │
     ┌──────▼──────┐
     │   CWE-196   │  stored in a signed variable  →  becomes −1
     └──────┬──────┘
     ┌──────▼──────┐
     │   CWE-839   │  the check only looks at the ceiling  →  −1 passes
     └──────┬──────┘
     ┌──────▼──────┐
     │   CWE-195   │  read as unsigned at the point of use  →  65535 bytes
     └─────────────┘
```

Three separate numbers, one root: **the same number was read three times under
three different contracts.**

---

## An Honest Note

MITRE's CWE-196 page lists **no observed examples (CVEs)** — unlike its sibling
[195](./cwe_195.md). In MITRE's own wording, this direction is *less common* than
signed-to-unsigned conversion.

That does not mean "harmless"; it means "appears less often in the records". Those
are not the same thing. An empty CVE table can have two causes: either the weakness
really is rare, or when it does occur it gets labelled under a different number —
here, most likely the overflow or the out-of-bounds write it produced.

---

## How It Is Prevented

The pattern is the same as the rest of this family: **ask before letting the
conversion happen.**

```c
if (a > SHRT_MAX) return ERROR;   // check that it fits BEFORE converting
short b = (short)a;
```

In practice these are added on top:

- **Use fixed-width types:** `uint16_t`, `int32_t`. How many bits a `short` has
  varies by compiler and platform; the uncertainty is half the bug.
- **Let the compiler tell you:** `-Wconversion -Wsign-conversion` surface these
  conversions as warnings. They are not on by default.
- **Pick the bound once and use the same type everywhere.** Every case in this
  family starts with the sentence "the same value travels under two different
  types."

---

## Summary — Keep in Mind

```
☐ A conversion does not change the bits; what changes is the rule you read them with.
☐ The 16-bit pattern 1111...1111 is 65535 unsigned and −1 signed. Both are correct.
☐ Harmless alone. The danger starts when that value becomes an index or pointer arithmetic.
☐ There is no negative in the unsigned world; the conversion undermines "it can't be negative".
☐ Its typical outcome is a write BEFORE THE START of a buffer, not past its end.
☐ Its parent is CWE-681; in the chain it is 196 → 839 → 195, i.e. the first link.
☐ MITRE lists NO CVE examples — rare does not mean harmless.
☐ Defences: check the bound before converting, use fixed-width types, turn on -Wconversion.
```
