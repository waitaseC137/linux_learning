# 👾 CWE-680 — Integer Overflow to Buffer Overflow

> **The name of the chain.** While a program is working out how much memory to
> allocate, a number overflows, too little space is reserved, and data is then
> written past the end of it.

| | |
|---|---|
| **Official name** | Integer Overflow to Buffer Overflow |
| **Its type** | A chain — not a single event, but the link between two events |
| **What comes before** | [CWE-190](./cwe_190.md) — the number overflows |
| **What comes after** | [CWE-787](./cwe_787.md) — the write goes out of bounds |
| **Where it is born** | [08 · Increment](../salterden_bilgisayara/08_increment.md#-the-security-bridge) |

---

## Why It Has Its Own Number

The observation that "190 sometimes leads to 787" is so common that it **got its
own number**. In CWE this is called a *chain* — one weakness giving birth to
another.

The classic pattern is exactly the `+1` circuit you built in
[lesson 08](../salterden_bilgisayara/08_increment.md):

```c
n   = 65535;
buf = malloc(n + 1);        // n+1 WRAPS → malloc(0), zero bytes
for (i = 0; i <= n; i++)
    buf[i] = ...;           // writes 65536 times → out-of-bounds write
```

> 🔑 The subtlety here: there is **no missing bounds check — there IS one.** The
> programmer allocated `n + 1` bytes and reasoned correctly. But because *the check
> itself* overflowed, it saw a small number and waved it through. The overflow
> **overturned** the check.

---

## There Are Two Boxes Here

It is common to draw this chain as a single three-stage line, but that is
misleading. There are really **two separate boxes**, and both of them overflow —
for different reasons:

```
   ┌──────────────────┐                      ┌──────────────────┐
   │      BOX 1       │                      │      BOX 2       │
   │   the integer    │  this number was     │  the allocated   │
   │  (16/32/64 bit)  │  used as a SIZE      │  space (buffer)  │
   │                  │ ───────────────────► │                  │
   │  a + b overflowed│                      │    4464 bytes    │
   │   →  4464        │                      │    allocated     │
   └──────────────────┘                      └──────────────────┘
         CWE-190              CWE-680               CWE-787
     box 1 overflowed      the wire between     box 2 overflowed
     (because the box       (the number changed  (because the box was
      is NARROW)             universes)           cut to the WRONG SIZE)
```

Box 1 overflows because it is **narrow** — it has a `2ⁿ` limit. Box 2 overflows
because it was **cut to fit a number that was believed and was wrong.** Two
separate events, two separate causes.

> 🔑 **`CWE-680` is not a third event; it is the name of the wire between them.**
> The moment a number that came out of the arithmetic world makes a decision in the
> memory world. It does not "happen" on its own — the label only goes into a report
> when the cause of a 787 was a 190. Like a crash into a wall caused by brake
> failure: two events, one case file.

## When the Number Decides Memory — Stagefright

**2015 · Android · ~950 million devices**

The most famous case in this family, and the chain above exactly as described.

Android's media parsing library (`libstagefright`) worked out how much memory to
allocate by reading and summing the chunk sizes inside an MP4 file. The sizes are
chosen so that the sum **wraps**:

```
length = a + b            →  overflowed, a small number came out
buffer = allocate(length) →  a SMALL space was reserved
copy the data             →  a LARGE amount of data was written
                              → it spilled past the end of the buffer
```

What made the case legendary was not the technique but **the trigger**: MMS. A
message arrived on the phone, and Android parsed the media to prepare the
notification **before the user ever looked at it**. Which means:

> The victim did not have to do anything. No touching, no opening, no tapping.
> The phone being switched on was enough.

That is called a **zero-click** vulnerability, and it is the most valuable class
there is.

The outcome changed how Android works: automatic MMS pre-fetching was turned off,
media parsing was split into separate restricted processes, and Android moved to a
**monthly security patch** schedule. That schedule is still Stagefright's legacy
today.

---

## How It Is Prevented

The chain is stopped at its **first** link — that is, in the size calculation:

```c
if (__builtin_add_overflow(a, b, &length)) return ERROR;   // true if it overflows
buf = calloc(count, size);     // NOT malloc(count * size)
```

The details, and why "checking afterwards" does not work:
[CWE-190](./cwe_190.md#why-the-check-disappears)

## Summary — Keep in Mind

```
☐ 680 is not an EVENT, it is the NAME of the wire between 190 and 787. A chain label.
☐ There are TWO boxes: the integer (overflows because it is narrow) and the buffer (because it was cut to the wrong size).
☐ A bounds check may well exist; it gets overturned when the thing that overflows is the check ITSELF.
☐ Stagefright: the MP4 size calculation wraps, a small space is allocated, large data is written.
☐ Zero-click over MMS: the user did not have to do anything at all.
☐ Android's monthly patch schedule is this incident's legacy.
☐ Cut the chain at the first link: check the size calculation before it overflows.
```
