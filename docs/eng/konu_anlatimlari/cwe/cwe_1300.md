# 👾 CWE-1300 — Improper Protection of Physical Side Channels

> **Physical side channel.** A device leaks what it is processing **physically**:
> ripples in the current it draws, the electromagnetic waves it radiates, even the
> sound it makes. The code can be flawless; the leak comes from the physics
> underneath the code.

## NandGame's Silent Assumption

When you built the relay in lesson 01, a gate had two states: conducting or not
conducting. In the game a gate works **for free** — it burns no energy, it does not
warm up, it makes no sound, it leaves no trace outside itself.

A real gate is not like that. Think of the relay: the coil draws current, the iron
core moves, the contact closes with a *click*. There is no mechanical movement in a
transistor, but the idea is the same — **changing state costs energy.**

> 🔑 The CWE here sits exactly where that silent assumption of the game breaks:
> **a gate leaks information to the outside while it works.**

---

## Why Current Carries Information

A gate sitting at `0`, or sitting at `1`, draws relatively little current. The real
consumption happens **at the moment of transition**: `0 → 1` and `1 → 0`.

```
   data:   0 0 0 0            data:   0 1 0 1
           ─────────                  ─┐ ┌─┐ ┌─
   current: flat, calm        current: a sharp peak at every transition
```

Now apply that to an encryption circuit. The circuit performs different operations
depending on the bits of the key. Different operations flip different numbers of
gates. A different number of gates draws **a different power curve**.

Someone watching that curve with a sensitive enough measuring instrument may be
able to make inferences about the secret number inside, even without seeing **what**
the computation is. MITRE's definition says precisely this: *"an adversary could
monitor physical phenomena to make inferences about secret data."*

The same idea runs through three separate channels:

| Channel | What is measured |
|---|---|
| **Power** | Ripples in the current the device draws |
| **Electromagnetic** | The waves the circuit radiates (contact may not even be needed) |
| **Acoustic** | High-frequency sound made by components |

## Real Cases

A few of the examples recorded on MITRE's CWE-1300 page. What they all share:
**there is no bug in the software.**

| Record | What happened |
|---|---|
| **CVE-2013-4576** | An RSA key is extracted from message encryption software by listening to the sound the computer makes — *acoustic cryptanalysis* |
| **CVE-2021-3011** | A private key is extracted from security microcontrollers over electromagnetic emissions |
| **CVE-2019-18673** | The number of lit pixels on a display changes power consumption; someone measuring power over USB can read the PIN being entered |
| **CVE-2019-14353** | The same pattern in a crypto hardware wallet: the number of illuminated pixels shows up in power consumption |
| **CVE-2020-28368** | In a virtualisation product, an AES key is recovered through a power-monitoring side-channel attack |

> 🔑 Note the last two rows: the thing leaking is not even the encryption circuit —
> it is **the screen**. The number of lit pixels shows up in the current, and the
> current tracks the digits being entered. That is the hard part of looking for side
> channels: the leak comes from the component you were not watching.

The field is not new either. Extracting keys through power consumption was defined
academically in the late 1990s by **Paul Kocher** and colleagues with their work on
*differential power analysis*. Since then, smart cards, hardware security modules
and crypto wallets have been designed against this threat.

## A Physical Side Channel Is Not a Microarchitectural One

These get mixed up, so let's separate them:

```
PHYSICAL side channel        →  physics leaking outside the device: current, waves, sound
                                measuring it usually needs ACCESS TO THE DEVICE
                                CWE-1300

MICROARCHITECTURAL           →  shared resources inside the processor:
side channel                    cache, predictors, timing
                                measurable remotely, in software — other CWEs
```

Both belong to the "information is leaking" family, and both have
**CWE-203 (Observable Discrepancy)** as their parent. But one needs an
oscilloscope and the other needs code.

---

## How It Is Prevented

MITRE lists two basic directions, both of which follow the logic of "destroy the
leak at its source":

- **Masking / blinding.** Mix the secret value with a random value before it enters
  the computation, then correct the result afterwards. The measured power curve is
  then related not to the real key but to a mask that changes every time.
- **Shielding and tamper resistance.** Make taking a measurement physically harder:
  coatings, filters, enclosures.

In practice these are added on top:

- Making the operation **independent of the data** — algorithms that always perform
  the same steps, rather than ones that take different paths depending on a key bit
- Avoiding early-exit comparisons (the child class **CWE-1255** is exactly this: a
  comparison circuit being open to a power side channel)
- Adding noise and random delay — not a solution on its own, but it raises the cost
  of measuring

> 💡 Note that none of this is "fixing a software bug". What is being fixed here is
> **the physical behaviour of the circuit.** That is why CWE-1300 is a **hardware**
> weakness and is not closed by a patch — it is solved in the design.

## Summary — Keep in Mind

```
☐ NandGame's gate works for free; a real gate spends energy when it changes state.
☐ The real consumption is at the transition: 0→1 and 1→0. If the data changes, the power curve changes.
☐ Three channels: power, electromagnetic emission, sound. All three carry the same idea.
☐ There is no bug in the software — the leak comes from the physics underneath the code.
☐ The leak can come from a component you were not watching: even the number of lit pixels on a screen.
☐ Physical side channel (needs an oscilloscope) ≠ microarchitectural side channel (measured with code).
☐ Defences: masking/blinding, shielding, a data-independent flow of operations.
☐ Not closed by a patch. Solved in hardware design.
```
