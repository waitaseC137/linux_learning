# 👾 CWE-1261 — Improper Handling of Single Event Upsets

> **Single event upset.** A charged particle strikes the circuit and a single bit
> flips. If the hardware has not accounted for that possibility, that one bit
> changes everything.

## NandGame's Third Silent Assumption

We have seen the first two: a gate spends no energy ([1300](./cwe_1300.md)), and a
gate always works correctly ([1247](./cwe_1247.md)). The third is even more
invisible:

> **The bit you wrote stays the same until you change it.**

In lesson 04 you loaded the meaning of *number* onto wires. `16` wires, `65536`
distinct patterns. That lesson never discussed wires changing by themselves —
because in the world of logic, there is no such thing.

In the world of physics there is.

---

## The Physics Side

MITRE's definition states the cause plainly: as a charged particle passes through
the medium it **ionises** it, creating electron–hole pairs. That charge can be
enough to flip the value held in a memory cell or a flip-flop.

```
before:  the cell holds 0
         ⚡ a particle passes through, leaving charge
after:   the cell reads 1        ← the circuit is not broken, the VALUE is
```

This is called a **soft error**, and the reason it is "soft" is this: the hardware
has not failed. The cell is fine; write to it again and it keeps working properly.
The only thing corrupted is the **value** it happened to be holding.

That is also why it is hard to catch: the error does not repeat. Run the same
program with the same input again and you get the right answer.

---

## Why This Is a Security Topic

"A random bit flipping" sounds more like bad luck than a security topic. MITRE's
answer is clear: it depends on **where** the bit flipped.

The example sentence on its own page is this: a bit flip that turns an ordinary
user's privilege into **root**. In a privilege field, a single bit is the answer to
the question "is this an administrator?"

> 🔑 Recognise the pattern? We said the same thing in
> [CWE-190](./cwe_190.md): the overflow itself is neutral, and the danger is
> decided by **where the overflowed number is used**. It is the same here — where
> the flipped bit happens to be.

---

## Tracking It with Lesson 04's Rule

The `n wires → 2ⁿ patterns` rule from lesson 04 turns into a diagnostic tool here.

If **exactly a power of two** has been added to a number, there is no arithmetic
mistake — **a single bit** has flipped:

```
     0000 1000 0000 0000     ← this bit flipped
   +
     4096 was added to a number   (4096 = 2¹²)
```

The same trace reads in hexadecimal too: a byte dropping from `C5` to `C4` is
`1100 0101 → 1100 0100` in binary — again, a single bit.

## Real Cases

**Belgium, 2003.** In an electronic election in Schaerbeek, an unexplained **4096**
votes were added to one candidate's tally. The number itself was the clue:
`4096 = 2¹²`. The official report said it was "most likely a spontaneous bit flip".
The error was caught and corrected; that the cause was a cosmic ray was never
proven.

**Super Mario 64, 2013.** During a speedrun, Mario was suddenly teleported up one
floor. The first byte of the height value had changed from `C5` to `C4` — a single
bit. Flipping that bit by hand reproduces the same teleport; what flipped it is
unknown. Home consoles do not have error-correcting memory.

The two examples on MITRE's own page show where the consequences can go:

| Example | What happened |
|---|---|
| **Network hardware** | A parity check catches a bit flip in memory but **cannot correct it**; the device restarts and two to three minutes of service is lost |
| **Pacemaker** | A bit flips at high altitude, the device enters safe mode and has to be reset at a hospital. More than that: the incident exposes a crash file, and analysis of that file leads to the discovery of **a cryptographic key embedded in the device** |

> 💡 The second row teaches two lessons at once. First: one physical event can open
> the door to a completely different weakness (an embedded key). Second: a parity
> check **detects but does not correct** — and detection without correction usually
> means a service outage.

## How It Is Prevented

MITRE lists two basic measures, both taken at design time:

- **Triple modular redundancy (TMR).** Place three copies of the
  security-critical module and have their outputs **voted on**. If a bit flips in
  one copy, the other two outvote it. The classic solution in space and aerospace
  electronics.
- **ECC and address interleaving.** Use error-correcting code in memories holding
  critical data — unlike parity it does not merely notice, it **corrects**. Address
  interleaving spreads physically adjacent cells across different words; even if a
  single particle flips two neighbouring cells at once, each word is left with only
  one bad bit and ECC can repair both.

This is why servers and flight systems use ECC memory. Most home computers and
games consoles do not — which is also the answer to why the Mario case was
possible.

## Summary — Keep in Mind

```
☐ The game's third silent assumption: the bit you wrote stays the same until you change it.
☐ A charged particle ionises the medium, and the charge it leaves flips the value in a cell.
☐ Soft error: the hardware is fine, only the VALUE at that moment is corrupted. Writing over it fixes it.
☐ Hard to catch because it does not repeat; run it again with the same input and the answer is right.
☐ It is a security topic because of WHERE the bit flipped — in a privilege bit, it means "root".
☐ A deviation of exactly a power of two = a single bit flip. 4096 = 2¹², C5 → C4 is one bit.
☐ Belgium 2003: +4096 votes, caught and corrected; a cosmic ray was never proven.
☐ Mario 64 (2013): the height byte went C5 → C4. A home console has no ECC memory.
☐ Parity detects but does NOT correct → restart → service outage.

```
