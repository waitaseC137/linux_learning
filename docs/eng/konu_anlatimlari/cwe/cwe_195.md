# 👾 CWE-195 — Signed to Unsigned Conversion Error

> **Incorrect conversion from signed to unsigned.** A negative number is moved into
> a type where negatives do not exist. The result is not "a bit wrong" — it becomes
> one of the **largest numbers** that type can hold.

## Sending a Negative Where No Negative Exists

[196](./cwe_196.md) went from unsigned to signed. This is its exact opposite — and
in practice far more damaging.

```c
int    n = -1;
size_t s = n;        // the same bits, a new reader
                     // s = 18446744073709551615
```

Again, no bit was lost. But in the unsigned world there is no place called
negative; the bit pattern of `−1` lands on the **largest** number there.

> 🔑 This ends up in the same place as `0 − 1 = 65535` from
> [CWE-191](./cwe_191.md), but **it arrives through a different door.** In 191 what
> overflows is a **calculation** (a subtraction happened and the result wrapped). In
> 195 there is no calculation at all — what overflows is a **conversion**. The same
> distinction exists between
> [CWE-190 and CWE-681](./cwe_681.md#how-it-differs-from-190): one is a calculation
> overflowing, the other a conversion.

---

## The Real Trap: When the "Error" Value Becomes a Size

MITRE's description names the most common form of the danger directly, and anyone
who writes C recognises the pattern: **many functions report failure by returning a
negative number.**

```c
ssize_t n = read(fd, buf, len);   // returns −1 on error
memcpy(dst, buf, n);              // n is read here as size_t
                                  // −1 → 18446744073709551615 bytes
```

When the error check is forgotten, what happens looks like a simple oversight. It
is not: **the failure itself becomes the weapon.** The program correctly reported
the moment things went wrong; the code that did not read that report mistook it for
an enormous size.

> ⚠️ The same pattern exists on the `malloc()` side: passed as a size, a negative
> value either becomes a very large allocation attempt or, after wrapping, a buffer
> **smaller** than needed. The second is the doorway to the
> [CWE-680](./cwe_680.md) → [CWE-787](./cwe_787.md) chain.

## MITRE's Recorded Examples

| CVE | What happened |
|---|---|
| **CVE-2025-27363** | In a font rendering library, a signed `short` is assigned to an unsigned `long`; the wraparound causes an **insufficient** buffer to be allocated and an out-of-bounds write |
| **CVE-2007-4268** | A signedness error in an integer comparison permits a heap overflow |

> 💡 Look at the first one: the whole chain is in a single line — **conversion (195)
> → insufficient allocation (680) → out-of-bounds write (787).** And the trigger is a
> font file, which means a user "merely opening a document" is enough. What MMS was
> to Stagefright, the font file is here.

## The End of the Chain

In the three-step example from lesson 09, 195 is the last link, and exactly where
the damage surfaces:

```
[196]  65535 stored in a signed variable      →  −1
[839]  if (len > MAX) only checks the ceiling →  −1 passes
[195]  memcpy reads the length as unsigned    →  65535 bytes copied
                                                  └─► CWE-787
```

Three numbers, one root: **the same pattern was read three times under three
different contracts.** The sentence from lesson 09 sits underneath the whole chain:

> **The pattern is the same, the meaning is the reader's decision.**

---

## How It Is Prevented

```c
ssize_t n = read(fd, buf, len);
if (n < 0) return ERROR;         // filter the error out FIRST
memcpy(dst, buf, (size_t)n);     // only then convert
```

As rules:

- **Never use an error return as a size.** The result of any function that can
  return a negative value must be filtered before it stands in for a size or index.
- **Both sides of a comparison should have the same type.** When C compares a signed
  with an unsigned value it silently converts the signed one to unsigned; the
  comparison is broken before it is even read.
- **Let the compiler tell you:** `-Wsign-conversion` and `-Wsign-compare` make these
  conversions visible; they are off by default.
- **Catch it at run time:** `-fsanitize=implicit-conversion`.

## Summary — Keep in Mind

```
☐ A negative converted to unsigned does not become "a bit wrong", it becomes the LARGEST.
☐ The bits do not change; what changes is the contract you read them under.
☐ Same destination as 191, different door: 191 is a calculation overflowing, 195 a conversion.
☐ The same distinction exists between 190 and 681 — this family keeps making the same fork.
☐ The most common trap: mistaking the result of an error-returning function for a size.
☐ The failure itself becomes the weapon; the program reported correctly, the reader misunderstood.
☐ CVE-2025-27363: font file → conversion → insufficient buffer → out-of-bounds write.
☐ The last link of the chain; its output is CWE-787.
☐ Defences: filter negatives BEFORE converting, match types in comparisons, turn on -Wsign-conversion.
```
