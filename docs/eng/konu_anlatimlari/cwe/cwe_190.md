# 👾 CWE-190 — Integer Overflow or Wraparound

> **Integer overflow.** A calculation is written on the assumption that the result
> will always grow. But when the result does not fit in its box, it does not spill
> out — **it wraps around.**

## The Danger Is Not in the Number, It's in the Number's Job

Let's draw this distinction first, because it is the backbone of the page:

```
65535 + 1 = 0   ←  NOT A BUG.
                   Normal, documented, designed machine behaviour.
                   In ℤ/2¹⁶ℤ this is simply the right answer.
```

The machine is not the one lying. The one lying is the program that mistakes that
`0` for a **total**.

So how much harm does that wrong number do? The answer depends on exactly one thing:

> **What does that number decide in the very next step?**

If it gets printed and forgotten — none. If it is the size of memory about to be
allocated — the whole device. Same overflow, same math, a chasm in between.

> 🔑 **How to read the cases below:** In each one, look for two things separately.
> **(1)** Which number overflowed? **(2)** What was that number deciding? The math
> of the cases is always the same; the second question is where they part ways.

---

## Harmless on Its Own

This matters: CWE-190 is a **weakness**, not a vulnerability by itself. A counter
can wrap and nothing happens.

For it to become dangerous, the overflowed value has to travel to **one of these
four places**:

```
1.  an allocation size    →  malloc(n)        →  a buffer SMALLER than needed
2.  a bounds check        →  if (i < n)       →  the check is OVERTURNED
3.  a loop counter        →  for(; i<n; )     →  never ends / runs too far
4.  an array index        →  buf[i]           →  access OUTSIDE the bounds
```

> 🔑 That is the question to ask during an audit: **where does this overflowable
> number go?** If it goes to none of the four, it is noise, not a finding. This
> distinction is what separates a good security report from noise.

## When the Number Decides Money — BEC Token

**April 2018 · Ethereum · CVE-2018-10299 · "batchOverflow"**

You do not need to know C, because this case **is not in C**. The language is
**Solidity** — a smart contract language. Overflow is not a C bug; it belongs to
**every** system that runs on `ℤ/2ⁿℤ`.

The contract had a function that sent tokens in bulk. In essence:

```
total = recipient_count × amount        ← 256 bits
if my_balance < total: reject           ← the check is RIGHT HERE
send amount to each recipient
```

There is a check. It even looks sensible. But the values passed in were chosen
like this:

```
recipient_count = 2
amount          = 2²⁵⁵                  ← enormous

total = 2 × 2²⁵⁵ = 2²⁵⁶   →   mod 2²⁵⁶ = 0
```

Now look at the check:

```
my_balance < 0 ?   →  NO.  ✅ passed.
```

The wallet could have been empty, it would have made no difference. No balance is
less than `0`. The check was passed with a clean bill of health — and then
**`2²⁵⁵` tokens were written into two wallets.** Out of nothing. An astronomical
amount.

The coin's value went to zero within hours and the major exchanges halted trading.
Other tokens with the same pattern were hit the same week.

> ⚠️ **The real lesson here is not whether there was a check, but its order.** The
> check **had been written** — but it was asked of an already-overflowed number. The
> right move was to ask *before* doing the multiplication. How the correct check is
> derived is in
> [08.5](../salterden_bilgisayara/08.5_sayac_basa_donunce.md).

After this incident the language itself changed: with **Solidity 0.8**, overflow
checking became **the default**. Anyone who wants to wrap must now write
`unchecked` explicitly.

> 💡 You see the same reflex in C: the only difference between `calloc` and
> `malloc(n * size)` is that `calloc` checks that multiplication **for you**. Two
> different worlds, the same patch on the same wound.

## When the Number Decides Time — Y2038

Unix time is a very simple idea: **the number of seconds since 1 January 1970.** A
single integer. No calendar, no months, no time zones — just a counter.

The problem is where that counter is kept. If it is a 32-bit **signed** integer,
its ceiling is:

```
2³¹ − 1 = 2,147,483,647 seconds
```

Added to 1970, that number lands here:

```
19 January 2038, 03:14:07 UTC     →  the largest value
        +1 second                 →  13 December 1901, 20:45:52 UTC
```

So the clock does not go forward — it goes **137 years back**. The reason is
familiar: the sign bit fills up and the number wraps into the negatives (the far
end of the circle from
[09_subtraction](../salterden_bilgisayara/09_subtraction.md)).

The difference from Y2K matters: **Y2K was a format problem** (writing the year
with two digits, a convention), **Y2038 is a type problem** — the physical limit of
the box the number is kept in. A convention can be changed; a box can only be made
bigger by changing code.

Where it hits:

- Embedded devices — boilers, meters, industrial controllers, vehicle units. They
  go years without an update.
- File formats and protocols that defined a 32-bit time field
- Certificate validity — what does a system do with a certificate whose expiry date
  falls in 1901? It either treats it as long expired, or the date comparison flips.

> 🔑 This overflow happens with **nobody attacking at all**. No attacker is needed;
> the calendar moving forward is enough. It is the clearest example of CWE-190
> doing damage without an attack.

Modern systems moved to 64 bits — that ceiling is longer than the age of the
universe, so the problem is closed. Where it is not closed is wherever nothing gets
updated.

## When the Number Decides a Machine — Boeing 787

**May 2015 · FAA emergency directive**

The 787's generator control units (GCUs) hold an internal counter. It increments
every **10 milliseconds**. It is 32-bit signed. When does it fill?

```
2³¹ × 10 ms = 21,474,836,480 ms
            = 21,474,836 seconds
            ≈ 248.55 days
```

If the aircraft stays **continuously powered for 248 days**, the counter overflows.
The unit reads this as an "inconsistent state" and drops into **safe mode** — and
safe mode means cutting the generators. Because all four generators are the same
age, **all of them do it at the same moment.** Possibly in flight.

The fix the FAA published is of a kind rarely seen in engineering:

> **Completely power the aircraft down and back up before 248 days.**

That is, reboot the plane.

> 💡 You are right to find that funny, but the engineering decision underneath is
> serious: a permanent fix required a software update, and airworthiness approval
> takes time. The directive was put in place as an **operational patch** for that
> interval. The software fix came later.

There is no security vulnerability in this case — no attacker, no malice, no data
leaking. A counter simply fills up. **CWE-190 in its purest form**: nobody worked
out what `2³¹` multiplications came to in days.

## When the Number Decides Nothing — Pac-Man

**1980 · the "kill screen" · level 256**

Pac-Man's level counter is **8 bits**. Its ceiling is `255`.

```
  11111111   = 255      (moving on to level 256)
+        1
 100000000   = 9 digits — but the box holds 8
 ↑
 this bit falls off   →   00000000 = 0
```

The game draws the fruit strip at the bottom of the screen "once per level". With
the counter at `0`, that loop runs unexpectedly long and fills the right half of
the screen with random characters. The level becomes unplayable.

This is not a vulnerability — nobody is harmed, nobody is attacking. But the
**math is identical** to the other cases. The only difference is what the number
was deciding.

> 🔑 That is exactly why this case is on the page: the overflow itself is neutral.
> The word "vulnerability" describes not the overflow but **where the overflowed
> number happened to be.**

## All Together

The math is the same in all of them. The only thing that changes is the second
column.

| Case | What the overflowed number was deciding | Outcome | CWE |
|---|---|---|---|
| **Stagefright** | the size of memory to allocate | remote code execution, zero click | [680](./cwe_680.md) → [787](./cwe_787.md) |
| **BEC Token** | the amount of money to send | tokens minted from nothing, the coin's death | 190 |
| **Y2038** | the date and time | logic collapse, certificate/comparison errors | 190 |
| **Boeing 787** | generator state | loss of electrical power in flight | 190 |
| **Ariane 5** | the rocket's horizontal velocity | destruction of the vehicle, $370 million | [681](./cwe_681.md) |
| **Pac-Man** | the level number | an entertaining glitch, no harm | — |

And the sentence from `08.5` sits underneath all six rows:

> **The program thinks it is in `(ℕ, +)`. It is actually in `(ℤ/2ⁿℤ, +)`.**

## Why the Check Disappears

How the correct check is derived is explained in
[08.5](../salterden_bilgisayara/08.5_sayac_basa_donunce.md): ask before letting the
overflow happen at all, i.e. `a > MAX - b`. There is one more step here — **even a
correctly written check can vanish.**

In C two types behave differently, and the difference is vital:

| type | overflow behaviour |
|---|---|
| **unsigned** | defined — wraps `mod 2ⁿ`, guaranteed |
| **signed** | **undefined behaviour (UB)** |

"Undefined" means the compiler **has the right to assume it never happens**:

```c
int a, b;
if (a + b < a)        // the classic overflow check
    return ERROR;
```

The compiler reasons: *"Signed overflow is UB, so it does not happen. If it does
not happen, `a+b` is always greater than or equal to `a`. Therefore this condition
is always false."*

**And it deletes the check during optimisation.**

> ⚠️ You really do see this in reverse engineering: the check is there in the
> source and has no counterpart in the disassembly. It is not a compiler bug — it
> is a permission the standard grants. This is why, before saying "there is no
> check" in a binary, you have to look at the **generated code**, not the source.

### How to do it right

```c
if (__builtin_mul_overflow(count, size, &total)) return ERROR;   // true if it overflows
buf = calloc(count, size);        // NOT malloc(count * size) — calloc checks
// when testing:  clang -fsanitize=integer
```

## So How Are These Found

Overflow is hard to find because, as
[08.5](../salterden_bilgisayara/08.5_sayac_basa_donunce.md) shows, the error set is
narrow: `E = {(a,b) : a+b ≥ 2ⁿ}`. **Outside** `E` the code works flawlessly. Normal
tests never enter `E` — nobody tries a length of `65535`.

So four approaches are used:

| Method | The idea |
|---|---|
| **Boundary value testing** | Not random values — try the **exact edges**: `0`, `1`, `MAX−1`, `MAX`, `MAX+1` |
| **Fuzzing** | Feed the program millions of malformed inputs and catch what crashes. Stagefright was found this way |
| **Static analysis** | Without running the code, flag expressions that can overflow |
| **Sanitizers** | Compile the program so it catches the overflow **as it runs** (`-fsanitize=integer`) |

> 💡 See the shared idea: all four do the same thing — **they deliberately try to
> get into the set `E`.** Normal use never goes there, and that is precisely where
> a bug can hide for years.

## Summary — Keep in Mind

```
☐ Overflow is harmless on its own. The harm is decided by what the number does next.
☐ Overflow is not specific to C — Solidity, embedded systems, flight software, games. Same math.
☐ The four dangerous places: allocation size · bounds check · loop counter · array index.
☐ BEC: the product wrapped to 0 and the "do you have enough balance" check passed clean. There WAS a check; its ORDER was wrong.
☐ Solidity 0.8 made overflow checking the default. Same reflex as calloc: the language fixed itself.
☐ Y2038: 19 January 2038, 03:14:07 UTC → 1901. No attacker needed, the calendar is enough.
☐ Y2K was a format problem (a convention), Y2038 is a type problem (the box's limit). The second needs code.
☐ Boeing 787: 2³¹ × 10 ms ≈ 248 days. The fix: reboot the plane. No attacker, just a counter.
☐ Pac-Man 256: eight digits filled and rolled over. Same math, zero harm, not a vulnerability.
☐ unsigned overflow is defined; signed overflow is UB → the compiler can DELETE even a correct check.
☐ Overflow is hard to find because E is narrow; the code is flawless outside it. Try the edges on purpose.
```
