# 👾 CWE-839 — Numeric Range Comparison Without Minimum Check

> **A range check with the lower bound forgotten.** The program checks whether a
> value exceeds a maximum, and lets it through. It never checks the minimum. But if
> the type can hold negative numbers, a negative value slips underneath the check.

## There Is a Check — but Only Half of One

The sneakiest thing about this family is not the **absence** of a check but its
**incompleteness**. Auditing the code, nothing jumps out at you:

```c
if (len > MAX)
    return ERROR;       // ✅ the upper bound is guarded
memcpy(buf, src, len);
```

Whoever wrote it reasoned correctly: "the length must not exceed the buffer." And
it does not. The only question they did not ask is: **can len be negative?**

If `len` is a signed type, it can. And a negative value sails through an
upper-bound check — because `−1 > MAX` is always false.

> 🔑 The bug is not an oversight, it is an **assumption**. In the programmer's head
> that variable was already positive; a length can't be negative, surely. But they
> **never wrote that contract into the type.** As long as the type permits
> negatives, "it can't" remains a wish.

---

## Not Only a Memory Problem

It is easy to mistake this weakness for a subspecies of buffer overflow. In its own
description MITRE gives a completely different example, and it shows the idea very
well:

A shopping application validates the quantity ordered — "you can't ask for more
than we have in stock" — by checking the upper bound. It does not check the lower
one.

```
quantity = −5   →   passes the upper-bound check
                    total = −5 × price = a negative amount
                    the negative amount is CREDITED to the account
```

The attacker is not buying a product; they are **selling** one to the shop. Without
a single memory address being touched.

> 💡 The lesson here: this weakness is not about memory, it is about an
> **arithmetic contract**. The memory cases are the loudest ones, but the root is
> the same — the range a number may occupy was only half described.

---

## MITRE's Recorded Examples

Some of the cases listed on the CWE-839 page. Watch the pattern repeat:

| CVE | What happened |
|---|---|
| **CVE-2010-1866** | An integer overflow produces a negative value, passes a maximum-only check, heap buffer overflow |
| **CVE-2009-1099** | A 16-bit counter is read as negative, compared against a 32-bit maximum → a write before the buffer |
| **CVE-2010-3704** | A parser uses `atoi()` with no negative check → a write before the buffer |
| **CVE-2010-2530** | A negative integer passes the size check → excessive memory allocation |
| **CVE-2008-4558** | A negative ID passes the maximum-index check → a read before an array's bounds |

The same sentence fits all five: **the check had been written, it was looking at
the ceiling, and the floor was empty.**

## The Middle of the Chain

In the three-step example from lesson 09, 839 is the middle link:

```
[196] stored in a signed variable       →  −1
   │
[839] if (len > MAX) only checks the ceiling  →  −1 PASSES
   │
[195] read as unsigned at the point of use    →  65535 bytes
```

This link is not our invention: in MITRE's own relationship table, **839 *CanPrecede*
[CWE-195](./cwe_195.md)**. The same table lists buffer underwrite (CWE-124) among
839's consequences.

---

## How It Is Prevented — and Why "Make It Unsigned" Is Not the Whole Answer

The most direct fix is to ask the question that was not asked:

```c
if (len < 0 || len > MAX)     // both ends at once
    return ERROR;
```

The second fix that comes to mind is: "if it must never be negative, make the type
unsigned." Reasonable, and usually right — but it **does not delete the problem, it
moves it.**

> ⚠️ An unsigned type has no negatives, so the `len < 0` check becomes meaningless
> too. But if the same variable is involved in a subtraction like `len - 1`, then a
> zero makes it wrap downward into an enormous number — you have moved to
> [CWE-191](./cwe_191.md). Whatever the type, the range check is still needed.

In practice these are added:

- Validate the value **at its source**, not where it is used. A number arriving from
  the network or a file is forced into range the moment it enters the program.
- Define the bound in one place and use the same constant in every check.
- Avoid converters that do not report failure, like `atoi()`; `strtol()` tells you
  about both errors and overflow.
