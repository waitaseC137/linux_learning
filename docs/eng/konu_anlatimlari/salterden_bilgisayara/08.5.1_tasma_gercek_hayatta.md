# 🌍 From Switches to a Computer — Interlude: Overflow in the Real World

> In the previous interlude (`08.5`) we set up the **mathematics** of overflow: the machine
> doesn't run on `(ℕ, +)`, it runs on `(ℤ/2ⁿℤ, +)`. This lesson looks at what that
> mathematics has actually done in the world — minted money, downed aircraft, blown up a
> rocket.

> The only question in this lesson:
>
> **The overflowed number was harmless on its own. What created the danger was who trusted
> that number. So the question "where can an overflow go?" is really the question "how
> important a thing is this number deciding?"**

> *(Interlude: short, no circuits, no game. Pour yourself a tea, read it, move on.)*

## The Danger Isn't in the Number, It's in the Number's Job

In `08.5` we drew this distinction; here it becomes the spine:

```
65535 + 1 = 0   ←  NOT A BUG.
                   The machine's normal, documented, designed behaviour.
                   In ℤ/2¹⁶ℤ that is simply the correct answer.
```

The machine isn't the one lying. The one lying is the program that mistakes that `0` for
**"the total"**.

So how much damage does this wrong number do? The answer depends on exactly one thing:

> **What does that number decide in the next step?**

If it gets printed to the screen and forgotten — none. If it's the size of the memory about
to be allocated — the whole device. Same overflow, same mathematics, a chasm in between.

> 🔑 **How to read this lesson:** In each case below, look for two things separately.
> **(1)** Which number overflowed? **(2)** What was that number deciding? The mathematics of
> the cases is always the same; the place they part ways is the second question.

## 💰 When the Number Decides Money — BEC Token

**April 2018 · Ethereum · CVE-2018-10299 · "batchOverflow"**

You don't need to know C, because this case **isn't in C.** Its language is **Solidity** —
a smart-contract language. Overflow is not a bug that belongs to C; it belongs to **every**
system that runs on `ℤ/2ⁿℤ`.

The contract had a function for sending tokens in bulk. Its essence was this:

```
total = recipient_count × amount        ← 256 bits
if my_balance < total: reject           ← the check is HERE
to each recipient: send amount
```

There's a check. It even looks sensible. But the attacker did this:

```
recipient_count = 2
amount          = 2²⁵⁵                  ← enormous

total = 2 × 2²⁵⁵ = 2²⁵⁶   →   mod 2²⁵⁶ = 0
```

Now look at the check:

```
my_balance < 0 ?   →  NO.  ✅ passed.
```

The attacker's wallet could have been empty, it wouldn't have mattered. There is no balance
below `0`. The check was sailed straight through — and then **`2²⁵⁵` tokens were written
into two wallets.** Out of nothing. An astronomical amount.

The coin's value went to zero within hours and the major exchanges halted trading. Other
tokens with the same pattern were hit the same week.

> ⚠️ **The real lesson here isn't the existence of the check, it's its order.** The
> programmer **wrote** the check — but asked the already-overflowed number. It's the exact
> counterpart of the sentence from `08.5`: *asking the culprit "are you the culprit?"* The
> right way was to ask **before** the multiplication happened.

After this event the language itself changed: with **Solidity 0.8**, overflow checking
became the **default.** Anyone who wants to overflow now has to write `unchecked`
explicitly.

> 💡 You've seen this reflex before: in C, the only difference between `calloc` and
> `malloc(n * size)` is that `calloc` checks that multiplication for overflow **internally.**
> Two separate worlds, the same patch on the same wound.

## ⏰ When the Number Decides Time — Y2038

Unix time is a very simple idea: **the number of seconds since 1 January 1970.** One single
integer. No calendar, no months, no time zones — just a counter.

The problem is where that counter is stored. If it's a 32-bit **signed** integer, its
ceiling is:

```
2³¹ − 1 = 2 147 483 647 seconds
```

Added to 1970, that number lands here:

```
19 January 2038, 03:14:07 UTC   →  the largest value
        +1 second               →  13 December 1901, 20:45:52 UTC
```

So the clock doesn't go forward, it goes **137 years back.** The reason is familiar: the
sign bit fills up and the number wraps into the negatives (the far end of the circle from
`09_subtraction`).

The difference from Y2K matters: **Y2K was a format problem** (writing the year with two
digits, a convention), **Y2038 is a type problem** — the physical limit of the box the
number lives in. A convention can be changed; a box can only be widened by changing code.

Where it bites:

- Embedded devices — boilers, meters, industrial controllers, vehicle units. They go
  unupdated for years.
- File formats and protocols — the ones that defined a 32-bit time field
- Certificate validity — what does a system do with a certificate whose "expiry date" drops
  to 1901? Either it treats it as long expired, or the date comparison flips.

> 🔑 This overflow happens **without anyone attacking.** No attacker is required; the
> calendar advancing is enough. It's the clearest example of CWE-190 doing damage with no
> attack at all.

Modern systems moved to 64 bits — that ceiling is longer than the age of the universe, so
the problem is closed. The places it isn't closed are the places that don't get updated.

## ✈️ When the Number Decides a Machine — Boeing 787

**May 2015 · FAA emergency directive**

The 787's generator control units (GCUs) have an internal counter. It increments every **10
milliseconds**. 32-bit signed. When does it fill up?

```
2³¹ × 10 ms = 21 474 836 480 ms
            = 21 474 836 seconds
            ≈ 248.55 days
```

If the aircraft stays continuously powered for **248 days**, the counter overflows. The unit
reads this as an "inconsistent state" and goes into **failsafe mode** — and failsafe mode
means cutting the generators. Since all four generators are the same age, **all of them at
once.** It could happen in flight.

The solution the FAA published is of a kind rarely seen in engineering:

> **Completely power the aircraft off and on again before 248 days elapse.**

That is, **reboot the aeroplane.**

> 💡 You're right to find that funny, but the engineering decision underneath it is serious:
> the permanent fix required a software update, and airworthiness approval takes time. The
> directive was put in place as an **operational patch** for that period. The software fix
> came later.

There's no security vulnerability in this case — no attacker, no malice, no data leaking.
Just a counter filling up. **CWE-190 in its purest form**: nobody worked out what the
product `2³¹ × 10 ms` came to in days.

## 🚀 When the Number Decides Physics — Ariane 5

**4 June 1996 · Flight 501 · ~370 million dollars**

The European Space Agency's new rocket lost control roughly **37 seconds** after launch on
its first flight and destroyed itself at the **39th second**.

The head of the causal chain was a single line. In the inertial reference system (SRI), a
horizontal velocity value was being converted from a **64-bit floating-point** number to a
**16-bit signed integer**.

On Ariane **4** this conversion was safe — because Ariane 4 didn't fly that fast and the
value always fit in 16 bits. The code was carried over to Ariane 5 **as is.** Ariane 5 was
more powerful and accelerated faster.

```
actual value  >  32767      →  didn't fit in 16 bits
```

What happened next:

1. The SRI raised a conversion error and shut itself down
2. The backup SRI took over — **but it was running exactly the same software**
3. With the same data, in the same second, it went down too
4. The flight computer read the error code as **flight data**
5. To correct a deviation that didn't exist, it swung the engines to full deflection
6. The rocket broke up aerodynamically and the destruct system fired

> ⚠️ **An honest note:** Technically this case isn't pure CWE-190 — it sits closer to
> **CWE-681 (Incorrect Conversion Between Numeric Types)** — what overflowed was not an
> addition but a **type conversion.** But the root cause is the same sentence: *the number
> was bigger than the box holding it and nobody asked.* When you're recognising cases in
> this family, look for that sentence rather than the class number.

The second lesson is independent of software and even more valuable: **redundancy that runs
the same software is not redundancy.** There were two systems, there was one bug, and both
went down at the same time.

The third: that computation **served no purpose at all on Ariane 5.** It was for pre-launch
alignment and had no reason to keep running after liftoff. It was left enabled because it
was a leftover from Ariane 4. **Dead code blew up a rocket.**

## 📱 When the Number Decides Memory — Stagefright

**2015 · Android · ~950 million devices**

The most famous case in the series, and precisely the chain we drew in `08.5`.

Android's media parsing library (`libstagefright`) computed how much memory to allocate by
reading and summing the chunk sizes inside an MP4 file. The attacker chooses the sizes so
that the total **wraps**:

```
length = a + b            →  overflowed, a small number came out
buffer = allocate(length) →  a SMALL region was allocated
copy the data             →  a LARGE amount was written
                              → it spilled outside the buffer
```

### There are **two** boxes here

It's common to draw this case as a three-stage chain, but that's misleading.
There are really **two separate boxes**, and both of them overflow — for
different reasons:

```
   ┌──────────────────┐                      ┌──────────────────┐
   │      BOX 1       │                      │      BOX 2       │
   │   the integer    │  this number was     │  the allocation  │
   │   (16/32/64 bit) │  used as a SIZE      │  (the buffer)    │
   │                  │ ───────────────────► │                  │
   │  a + b overflowed│                      │   4464 bytes     │
   │   →  4464        │                      │   allocated      │
   └──────────────────┘                      └──────────────────┘
         CWE-190              CWE-680               CWE-787
      box 1 overflowed     the wire between      box 2 overflowed
      (because the box     (the number changed   (because the box was cut
       is NARROW)           universes)            to the WRONG MEASUREMENT)
```

Box 1 overflows because it is **narrow** — it has a `2ⁿ` limit. Box 2 overflows
because it was **cut while believing a wrong number.** Two separate events, two
separate causes.

> 🔑 **`CWE-680` is not a third event, it is the name of the wire between them.**
> The moment a number that came out of the arithmetic world makes a decision in
> the memory world. It doesn't "happen" on its own — the label is written on the
> report only when a 787's cause was a 190. Like "wall collision due to brake
> failure": two events, one file name.

### It overflows, but where to?

The natural question: the buffer is `0` bytes, but the data is `65536` bytes.
**Where does that data go?**

In the physical world the answer is easy: if your box is too small the items
fall on the **floor.** The floor is empty and nobody gets hurt.

**In memory there is no such thing as a floor.**

Memory is not an empty room; it is **a shelf packed side by side, with no gaps,
full to the end.** Where your region ends, empty space does not begin —
**somebody else's region begins.**

```
 ...┌─────────────┬─┬─────────────┬─────────────────┐...
    │  somebody    │ │  somebody   │   somebody      │
    │  else's data │ │ else's data │  else's data    │
    └─────────────┴─┴─────────────┴─────────────────┘
                  ↑
             your buffer
        (0 bytes — no width, but it HAS a place)
```

> 🔑 The data doesn't overflow into anywhere — **it writes over the neighbour.**
> There is no "outside" in memory. Writing outside your own boundary is always
> writing **inside somebody else's.**

One more subtlety: when you ask for `0` bytes, the system does not say *"no."*
It gives you a **valid address** — a real point on the shelf. It's just that the
width that belongs to you from that point on is zero. The consequence: the writes
**succeed.** No error, no warning, the program doesn't even pause. `08.5`'s first
sentence holds here too: **the machine does not object.**

> 💡 Think of the inverse: if the system had given no address at all, the program
> would crash on the first write. Ugly but **safe** — the bug surfaces
> immediately. The real danger isn't the region being **absent**, it's the region
> being **real but too small.** Working silently is what makes it dangerous.

So what is in the neighbour, and what does overwriting it get you? **That's not
this lesson's subject** — you go there after memory, stack frames and addressing
have been built. The door is here:
[binary_exploitation](../binary_exploitation/00_buradan_basla.md).

---

What made this case legendary wasn't technical, it was **the trigger:** MMS. A message
arrived on the phone, and Android parsed the media to prepare the notification **before you
even looked at it.** Which means:

> The victim didn't have to do anything. No touching, no opening, no tapping. The phone
> being switched on was enough.

That is called a **zero-click** vulnerability, and it is the most valuable class there is in
the vulnerability world.

Its consequences changed how Android works: automatic MMS pre-fetching was turned off, media
parsing was split into separate, restricted processes, and Android moved to a **monthly
security patch** schedule. That schedule is still Stagefright's legacy today.

## 🎮 When the Number Decides Nothing — Pac-Man

**1980 · the "kill screen" · level 256**

Pac-Man's level counter is **8 bits.** So its ceiling is `255`.

```
  11111111   = 255      (moving to level 256)
+        1
 100000000   = 9 digits — but the box holds 8
 ↑
 this bit falls off   →   00000000 = 0
```

The game draws the fruit strip at the bottom of the screen "as many as the level number".
When the counter is `0` the loop runs unexpectedly long and fills the right half of the
screen with random characters. The level becomes unplayable.

This is not a CWE — nobody is harmed, nobody is attacking. But **the mathematics is
identical to Stagefright's.** The only difference is what the number was deciding.

> 🔑 That is exactly why this case is here: the overflow itself is neutral. The word
> "vulnerability" describes not the overflow but **where the overflowed number ended up.**

## 🕵️ And One Made-Up Case — Gandhi

The most-told overflow story goes like this: *In Civilization, Gandhi's aggression value is
`1`; when he adopts democracy it drops by `−2`; `1 − 2` in an unsigned 8-bit value wraps to
`255`; and the world's most peaceful leader suddenly starts a nuclear war.*

**This story isn't true.** Sid Meier — the game's designer — wrote plainly in his own memoir
that no such bug existed. The story appeared on the internet in the 2010s and became a
legend.

The reason I'm stopping here isn't that the story is false. It's **why it was so easy to
believe.**

- The described mechanism is **real.** `1 − 2` in unsigned 8 bits really is `255`.
- The outcome is **familiar.** Everyone has seen software behave absurdly.
- And the story is **good.** An icon of peace launching nukes is funny.

> ⚠️ Reading security material you'll meet this trio often: accounts whose mechanism is
> correct and whose case is invented. The right reflex — learn the mechanism, **verify the
> case at its source.** A CVE number, a vendor bulletin, a CERT note, an official accident
> report. Every other case listed in this lesson has such a record; Gandhi's has none.

## The Whole Table

The mathematics is the same in all of them. The only thing that changes is the second
column.

| Case | What the overflowed number decided | Outcome |
|---|---|---|
| **Stagefright** | the memory size to allocate | remote code execution, zero-click |
| **BEC Token** | the amount of money to send | minting tokens from nothing, the coin's death |
| **Y2038** | the date and time | logic collapse, certificate/comparison errors |
| **Boeing 787** | generator state | loss of electrical power in flight |
| **Ariane 5** | the rocket's horizontal velocity | destruction of the vehicle, 370 million dollars |
| **Pac-Man** | the level number | an amusing glitch, no harm |

And `08.5`'s sentence stands underneath all six rows:

> **The program thinks it's in `(ℕ, +)`. It's actually in `(ℤ/2ⁿℤ, +)`.**

## So How Are These Found

A short look — the road ahead in this series.

Overflow is hard to find because, as you saw in `08.5`, the bug set is narrow:
`H = {(a,b) : a+b ≥ 2ⁿ}`. **Outside** `H`, the code works flawlessly. Ordinary tests never
enter `H` — nobody tries a field of length `65535`.

So four routes are used:

| Method | The idea |
|---|---|
| **Boundary value testing** | Not random — try the **exact edges**: `0`, `1`, `MAX−1`, `MAX`, `MAX+1` |
| **Fuzzing** | Feed the program millions of malformed inputs, catch what crashes. Stagefright was found this way |
| **Static analysis** | Without running the code, flag expressions that could overflow |
| **Sanitizers** | Compile the program so it catches the overflow **at runtime** (`-fsanitize=integer`) |

> 💡 See the shared idea: all four are doing the same thing — **deliberately trying to get
> into the set `H`.** Because normal use never goes there, that's where a bug can stay
> hidden for years.

## Summary — Keep in Mind

```
☐ Overflow is harmless alone. The harm is set by what the number does in the next step.
☐ Overflow isn't specific to C — Solidity, embedded systems, flight software, games. Same math.
☐ BEC: the product wrapped to 0 and the "do you have the balance" check sailed through.
☐ Do the check BEFORE the overflow. Asking an overflowed number = asking the culprit.
☐ Solidity 0.8 made overflow checks the default. Same reflex as calloc: the language fixed itself.
☐ Y2038: 19 Jan 2038, 03:14:07 UTC → 1901. No attacker needed, the calendar is enough.
☐ Y2K was a format problem (convention), Y2038 is a type problem (the box's limit).
☐ Boeing 787: 2³¹ × 10 ms ≈ 248 days. The fix: reboot the aeroplane. No attacker, just a counter.
☐ Ariane 5: 64-bit float → 16-bit int. Technically CWE-681, same root cause.
☐ Ariane's lesson: a backup running the same software is not a backup. And dead code blows up rockets.
☐ Stagefright: zero-click via MMS. The 190 → 680 → 787 chain, exactly.
☐ There are TWO boxes: the integer (overflows because it's narrow) and the buffer (wrong measurement).
☐ CWE-680 is not an EVENT, it's the NAME of the wire. Where a number crosses from arithmetic to memory.
☐ There is no empty space in memory. Writing outside your bounds = writing inside someone else's.
☐ allocate(0) doesn't error, it returns a VALID address → the writes succeed silently.
☐ Pac-Man 256: eight digits filled, wrapped to the start. Same math, zero harm. Not a CWE.
```
